## 1. 记账口径：为什么"等价参数预算"原先没有成立（**R3.21 的真正答案**）

审稿人问的是"如何保证有效参数预算等价"。实测答案是：**原先的记账口径下不可能等价**，
因为 **LoRA 的每 rank 参数成本在块间并不相等**。

Qwen2-VL-2B 实测（`tools/_p420_arch_probe.py` → `outputs/analysis/p3_alloc_budget_probe.json`）：

| 块 | 被适配 Linear 数 | `cost_k` = 每 rank 参数量 | 占比 |
|---|---|---|---|
| `vision` | 128 | **655,360** | 36.2% |
| `llm_shallow` | 42 | **247,296** | 13.7% |
| `llm_mid` | 98 | **577,024** | 31.9% |
| `llm_deep` | 56 | **329,728** | 18.2% |
| **合计** | **324** | **1,809,408** | 100% |

`cost_k = Σ_{Linear ∈ k}(in_features + out_features)`；
**成本模型已逐位断言**：同一脚本里用 `get_peft_model` 实测 r=8 的逐块可训参数量，
四块与 `8 × cost_k` **完全相等**（`:: hard_assert_cost_model[*].match == true`）。

**直接后果（这是稿件必须改的地方）**：
uniform rank 4（论文现在的 Theory 组做法）给出的逐块参数量是

```
vision 2,621,440 ／ llm_shallow 989,184 ／ llm_mid 2,308,096 ／ llm_deep 1,318,912
```

**最大 / 最小 = 2.65×**（来源：`tools/_p438_alloc_plans.py` →
`outputs/analysis/p3_alloc_plans.json :: key_fact_rank_uniform_neq_param_uniform`）。
即 **"rank 均匀"不等于"参数均匀"**。

> **⇒ 稿件 `experiments.tex` 第 264 行现在写的是
> "we compare three groups under an equal \emph{rank} budget
> ($\sum_k \mathrm{rank}_k = C = 64$, following~(A3))"** —— 口径已明确（Lead 于
> commit `c58f668` 修正）。但"rank 预算相等"**不等于"有效容量相等"**，见下一小节。

### 1.1 论文现有 Random 组的容量范围（R3.21 的真正症结）

稿件 `experiments.tex` 第 269–270 行的 Random 组定义：
*"Rank randomly drawn from $\{4,16,32,64\}$"*，且 rank 是**均匀施于全部模块**的
（与 Theory 组 $r=4$ 同一施加方式）。因此该组任一 run 的可训参数量为
`C · Σ_k cost_k`，其中 `C ∈ {4,16,32,64}`：

| `C` | 参数量（= `C × 1,809,408`） | 相对 Theory 组（`C=4`） |
|---|---|---|
| 4 | 7,237,632 | **1×** |
| 16 | 28,950,528 | **4×** |
| 32 | 57,901,056 | **8×** |
| 64 | 115,802,112 | **16×** |

（`Σ_k cost_k = 1,809,408` 的出处见上表；乘法为算术。）

⇒ **Random 组同时改变了"分配方式"与"总容量"两个因素**，而稿件把
$\sigma$ 大 30×（`808 vs 27`）归因于"分配不确定性"。
**这正是 R3.21 追问的"如何保证有效参数预算等价"**：
现有设计下**无法**保证，因为参数量本身跨了 16 倍。

> 本实验的做法：Random 组从**精确同参数**可行集抽样
> （`p3_alloc_plans.json :: exact_budget_allocations`，共 15 个方案，
> 每个都 `Σ rank_k·cost_k == 7,237,632`），从而把"分配方式"与"容量"解耦。

## 3. 分配律的实现（Corollary 2 / Eq. 5）

论文 `theory.tex` Eq. 5：

```
rank*_k = C · exp(−β·|Γ_k|) / Σ_j exp(−β·|Γ_j|)
```

**方向**（易被误读，稿件自己澄清过两次）：`exp(−β|Γ|)` ⇒
**|Γ| 越大的块 rank 越小** —— 在 alignment-sensitive 块上少给容量，
把预算集中到 `|Γ|` 最小的块。Appendix D 称其为 "hard-protection configuration"。

### 3.1 分配到"参数预算"下需要一步修正（**建议写进 Appendix**）

论文 (A3) 把预算写成 `Σ rank_k = C`（**rank** 记账）。若换成审稿人要求的
**参数**记账 `Σ rank_k·cost_k = B`，重做 KKT：

```
min Σ|Γ_k|·rank_k + (1/β)Σ rank_k log rank_k   s.t.  Σ rank_k·cost_k = B
⇒ log rank_k = −β|Γ_k| − βλ·cost_k − 1
⇒ rank_k ∝ exp(−β|Γ_k|) · exp(−βλ·cost_k)
```

即**多出一个 `exp(−βλ·cost_k)` 因子**，归一后等价于 `rank*_k ∝ w_k / cost_k`
（`w_k` 为 softmin 权重）。论文 Eq. 5 漏掉该因子 ⇔ 隐含假设所有 `cost_k` 相等。

本实验**两个变体都跑**并都归档：
- `exp_beta_*`：**论文字面**形式（`rank*_k = R·w_k`，R = 与 uniform 同口径的 Σ rank）；
- `exp_ca_beta_*`：**cost-aware KKT** 形式（`rank*_k = B·w_k/cost_k`）。

实测两者在 Qwen2-VL-2B 上给出**不同**的解（差 2.65× 的成本 ⇒ 不可忽略）。

### 3.2 分配数学的单元测试（**0 项失败**）

`tools/_p435_tests_alloc_math.py`（纯 CPU，秒级）用**合成 Γ**（跨 10²–10⁸、
含正负号、含几乎相等）验证以下性质，全部 PASS：

| 编号 | 性质 | 结果 |
|---|---|---|
| §0 | 预算可行性与最小成本下界（`Σcost = 1,809,408`） | PASS |
| §0b | `cost_k` 不等 ⇒ rank 均匀 ≠ 参数均匀（**R3.21 症结**） | PASS |
| §1 | `softmin_weights` 归一化 + **数值稳定**（β 大且 |Γ| 跨量级不 inf/nan） | PASS |
| §2 | Eq. 5 整数解 `Σ rank_k·cost_k == B` 逐位精确、`rank_k ≥ 1` | PASS |
| §3 | **单调性**：β↗ ⇒ 高|Γ|块 rank 不增、低|Γ|块 rank 不减 | PASS |
| §4 | **β→∞ ⇒ 线性目标 `Σ|Γ_k|·rank_k` 最优**（Appendix D 的 hard-protection 说法） | PASS |

此时**"最优排序"本身也无意义**（排序由 0.3% 的差异决定）。该情形在真实数据上不出现（见 §7 的分离度）。

   **但 3e-4 下反而更差**（+5968 vs +2842）⇒ **优势随 lr 反转，不能作为稳健主张。**
2. **🔴 匹配任务损失后，Γ-guided 的分配未显示优势**：
   若把两侧对齐到相近的 `loss_last`（0.5872 vs 0.5826），则
   **`exp` 落后于 `uniform`（+5967.8 vs +2842.1）** ⇒
   **原先"Γ-guided 在 5e-5 下更优"很可能是"训练得更少"的副产物，而不是分配规则的功劳。**
   这是本任务**对自身先前结论最强的反证**。
3. **AdaLoRA 的两档仍优于全部 Γ 侧方案**（−1468.2 / −757.3 vs 最好 +1477.5）。
   ⇒ **AdaLoRA 的优势在对称调 lr 后依然成立**（与 Lead 的预期一致）。
   **且 `3e-4` 档的 E 轨迹单调降（22003），`1e-3` 档震荡（27331 尖峰）** ⇒ **loss 低 ≠ 能量稳。**

> **⇒ 最终建议的稿件定位（能站住）**：
> **本方法的价值在于"零样本、分配决策不含目标模型梯度"，而不是在 ΔE 上取胜。**
> 我们**如实报告**：在能对目标模型调参/搜索的场合，AdaLoRA 更优；
> 本方法的适用场景是**不能或不愿在目标模型上做搜索**的情形。

### 8.0 🔧 通用工程教训（**建议全项目采用**）

#### 8.0.1 不要把聚合产物当来源

> **不要把聚合产物当来源。** 聚合文件若会被后续调用**重写**，它的字段路径就会**静默失效**。
> **来源必须是"只增不改"的逐 run 明细。**
> 本项目铁律"每个数字要能指名归档文件与字段"，**隐含要求那个文件是稳定的**。

**本任务的具体实例（真实发生、已修）**：
`tools/_p434_alloc_train.py` 每次调用都会重写 `<tag>/summary.json`，且**只包含本次调用涉及的方案**。
P1 补跑时我只传了 10 个 random 方案 ⇒ 该文件里
**`uniform` / `exp` / `corner` / `inverse` 四个规则方案全部消失**，
`tools/_p440_aggregate.py` 读到后**静默丢掉对照臂**（由 Lead 发现"字段出处失效"）。
**修法**：`_p440` 改为读**逐 run 的独立 JSON**（`<tag>/<plan>__seed<k>.json`，只增不改），
并跳过 `summary.json` 与非 run 文件（如 `adalora_probe.json`）；修后 **45 run / 15 方案全部恢复**。

#### 8.0.2 🔴 "静默覆盖类缺陷"三级危害排序（**错标 > 覆盖 > 重写**）

本任务连续抓到**三类同族缺陷**，**共同特征：两个不同的事实指向同一个存储位置，且失败是静默的**
（不报错、不崩溃、不丢文件）：

| 级别 | 现象 | 可见性 | 本任务的实例 |
|---|---|---|---|
| **重写** | 聚合产物每次被重写，丢掉未参与本次调用的方案 | **可见**（"少了一个"） | `_p434` 重写 `<tag>/summary.json` ⇒ P1 补跑时 4 个规则方案消失 |
| **覆盖** | 参数/tag 缺失导致多个配置写同一文件 | **可见**（"少了一个"） | `_p451` 原**无 `--tag`** ⇒ 两个 lr 会写同一 `adalora__seed42.json` |
| **🔴 错标** | **所有产物都在、数字都真实，只是标签与内容不符** | **不可见** —— 任何下游推断都会错，且**没有任何迹象提示你去查** | `_p434` 汇总归档曾写模块级常量 `"lr": LR`（恒 5e-5），而逐 run 与优化器用 `args.lr` ⇒ lr 扫描时"文件名写 1e-3、逐 run 写 1e-3、**汇总写 5e-5**" |
| **🔴 错标（更隐蔽的变体）** | 参数**根本不存在** ⇒ 传了也被忽略，配置全按默认跑、标签却写着新值 | **不可见** | `_p434` 原**无 `--lr`**；`--tag` 缺失时的同类风险 |

**⇒ 防御（两条，缺一不可）**：

1. **来源用"只增不改"的逐 run 明细**；每个会改变结果的配置都必须**落到文件名或归档字段**。
2. **写归档前从真实对象回读并断言**（比人工比对可靠）：

```python
_actual_lr = opt.param_groups[0]["lr"]            # 优化器**实际**用的
assert _actual_lr == args.lr == rec["lr"], \
    f"[配置错标] optimizer={_actual_lr} args={args.lr} archive={rec['lr']}"
```

**同理可从 processor 回读 `max_pixels`、从训练循环计数回读 `epochs`。**
⇒ 这条能挡住**所有"参数传了但没生效"**的情形，且**不依赖人去比对哪一行**。

3. **机器穷举检查器**：`tools/_p461_check_config_mislabel.py`
   —— 比较每个汇总归档的配置键与其**逐 run** 的对应键，不一致即以逐 run 为准修复并记台账。

**⚠️ 判据要两步，否则会产生假阳性**（Lead 的扫描第一版就踩了）：
① 归档字段写模块级常量，且同文件有对应 CLI 参数；**且**
② 该常量**在文件中没有任何被重新赋值的语句**（`globals()["C"]=…` / `C = args.…`）。
只看 ① 会把"**常量被动态覆盖**"的合法模式（如 `_p464` 把 `MIN_PIX/MAX_PIX` 用 `globals()` 回写）
误判为 bug —— Lead 的 161 脚本穷举因此有 **8 处假阳性、1 处真 bug**。
